## Protocol map (source inspection, 2026-11-13)
- `network.c`: TCP port 3490; new peers receive a text welcome prompt; `n <name>` renames; `b <version>` enters bot protocol. Version 0 maps to protocol 4. To avoid legacy behavior and obtain `MSG_GAMEMODE` plus on-demand energy, target protocol 8: versions 7–8 receive game mode, versions >=8 can request own energy with `u`; shot-begin is >=5 and shot-finish is >=6. Correction to earlier note: own energy is not pushed continuously; a client must request it with `u`, and this is supported at version >=8.
- Incoming event IDs/frames: 1 own ID (type,id); 2 player leave (type,id); 3 player position (type,id,f32 x,f32 y); 4 legacy shot finished (type,id,u32 point_count, points as f32 pairs); 5 shot begin (type,id,f64 angle,f64 velocity); 6 shot finish (type,id,f64 angle,f64 velocity,u32 point_count, points as f32 pairs); 7 game mode (type,id,u32 mode); 8 own energy response (type,id,f64 energy); 9 planet positions (type,count,sizeof(SimPlanet), then each planet's f64 x/y/radius/mass).
- `sendPlanets` sends planets during bot negotiation and on reinitialize only if server setting `sendplanets 1` is enabled. Its `SimPlanet` is 32 bytes (two doubles position + radius + mass); fields are copied into the 32-byte record at offsets 0/8/16/24.
- Bot commands are text lines: `n name`, `b 8`, `v velocity`, numeric angle line, `u` request energy, and `q` disconnect. Existing bot example sends velocity then angle.
- Server runs continuously; no game identifier appears in this protocol. It initializes simulation once and loops forever. A connection therefore gives a reliable capture start/stop boundary, but the wire stream cannot automatically group a reconnect with its earlier connection.

## Library research (maintainer docs checked 2026-11)
- Rust `TcpStream` has the necessary synchronous TCP operations; no Telnet option negotiation exists in NewtonWars source. The `telnet` crate implements Telnet control negotiation; avoid it because this is custom mixed text/binary TCP and Telnet control-byte handling would be extra/conflicting machinery. Use std `TcpStream` with a local NewtonWars framing parser: https://doc.rust-lang.org/std/net/struct.TcpStream.html and https://docs.rs/telnet/latest/telnet/.
- `rusqlite` is synchronous and its `bundled` feature avoids system SQLite discovery/version drift at compile-time cost and requires a C toolchain. Recommendation: use rusqlite + bundled for the local application: https://docs.rs/crate/rusqlite/latest.
- Math recommendation: defer numerical dependencies until model/observations are designed. `nalgebra` is a matrix library; `adskalman` is linear Kalman/RTS with caller-side linearization needed for nonlinear observation models. Avoid selecting an estimator crate before modeling: https://docs.rs/nalgebra/latest/nalgebra/, https://docs.rs/adskalman/latest/adskalman/, https://docs.rs/kalman_filters/latest/kalman_filters/extended/.
- Random names: `rand` supports choosing from a curated slice via `IndexedRandom::choose`; pin the crate and use its current API: https://docs.rs/rand/latest/rand/seq/trait.IndexedRandom.html.

### Round 27 — define uncertainty as evidence and prediction reliability (2026-11-21)
- User correction: uncertainty must guide information availability and simulation stability. The current covariance-only layer is fundamentally too narrow. The field should start broadly unknown and reduce with informative observations, including information a trajectory gives about planet parameters away from the sampled coordinates. The uncertainty viewer currently emits only `sqrt(trace(J Σ Jᵀ))`; null covariance makes every cell missing. The residual field has no uncertainty/covariance of its own.
- Terminology: **planet/map belief** is the hypotheses over source count, center, radius, and mass; **residual correction** is the estimated mean gravity left after the planet field; **residual uncertainty** is uncertainty in that correction (not its magnitude); **evidence availability/support** records how much independent, informative path evidence constrains a location/model; **epistemic field uncertainty** combines uncertainty over planet hypotheses and residual correction, plus model uncertainty where evidence is absent; **trajectory/simulation stability** measures how much a particular simulated path and its terminal outcome change across plausible maps, physics, and player states. **Parameter covariance** remains one conditional input to field uncertainty, not its synonym. Do not label any of these as calibrated probability without calibration.
- The user's initial "100%" is best represented initially as maximum *unknownness / no usable evidence*, not as a 100% probability of error. Keep field support, residual mean, residual uncertainty, and simulation stability as distinct diagnostics first; a single confidence number would hide incompatible causes and lacks a common calibrated scale. The user suggests the eventual field-level risk should mix unexplored space and residual information. Refine that as: unexplored/model-unsupported regions raise epistemic uncertainty; observed residual magnitude updates the correction mean, while residual consistency, independent support, and held-out prediction determine uncertainty in that correction. Large repeatable residual can be well predicted; small residual in an unexplored region remains uncertain. Residual structure can also be evidence for a missing/misestimated planet and should influence planet hypotheses, while a well-supported local residual may make the total gravity correction relatively certain without identifying the planet's geometry or proving a collision surface exists.
- Information from a trajectory is global through its sensitivity to shared planet parameters: different paths can constrain the same distant source. Information gain should account for observation noise/quantization, path termination, sensitivity and independent geometry; repeated nearly identical paths should add less than a new informative direction. This calls for model-parameter posterior/sensitivity or a hypothesis ensemble, not only distance-to-track. Current `LocalField::residual` has a fixed 40-unit support radius, which is a practical interpolation boundary for its mean residual, not a valid boundary for the information content of the trajectory or for global map uncertainty.
- Recommended staged estimator design: (1) expose `evidence availability`, `planet conditional covariance`, `residual mean/support/uncertainty`, and `model adequacy` separately, with explicit unavailable status; (2) maintain plausible whole-map alternatives or an approximation to their posterior, including no-source/missing-source uncertainty; derive field distribution by evaluating those alternatives plus conditional parameter covariance and a residual-correction distribution; (3) for a selected/few shot candidates, simulate a bounded set of plausible model/physics/player states and report path spread, termination/outcome disagreement, and collision margins as *scenario sensitivity*, not probabilities; (4) validate per map epoch on frozen multi-seed worlds and prequential held-out shots, checking field error, trajectory spread coverage, false predicted hits/termination switches, and reductions after informative versus duplicate paths. Confirm engine/simulator parity before treating stability scores as operational.
