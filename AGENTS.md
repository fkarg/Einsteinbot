# Project instructions

## Project context

This repository is **Einsteinbot**, a Rust project to build an information-gathering bot for [NewtonWars](https://github.com/Draradech/NewtonWars). The NewtonWars source checkout is expected at `../NewtonWars` and is the reference for its build process, runtime behavior, and client protocol.

The project target is to infer planet locations and gravity effects efficiently, maintain an incrementally updated map with uncertainty, and use that model to improve shot selection. Reinforcement learning is explicitly a later possibility, not an initial requirement.

For estimator evaluation, prioritize gravity-field accuracy in explored areas; also assess whole-field and unexplored-area accuracy, planet collision geometry, uncertainty, and trajectory prediction separately. Targeting and strategy ultimately optimize shot outcomes and game strength, not the estimator's field score alone. Use oracle truth only for evaluation, never as fit input. See [`docs/estimator-evaluation.md`](docs/estimator-evaluation.md) for the proposed scorecard and measurement semantics.

## Development direction

- First understand how to build and run the local NewtonWars game.
- Build a basic Rust telnet/TCP client and map the communication protocol before concentrating on bot strategy.
- Keep transport, protocol parsing, game state/map estimation, simulation, targeting, and bot policy modular, with clear interfaces.
- Keep early automated coverage small and focused on core behavior.
- Bias toward action: build a small end-to-end slice before spending time refining the design.
- Test uncertain details cheaply with local source inspection, synthetic examples, stored captures, or the local oracle when available; ask only when a real architectural tradeoff cannot be resolved by a reversible experiment.
- Prefer implementing a reasonable baseline and learning from its behavior over extended speculative design. Keep unresolved ideas explicit, but do not let them block independent implementation work.

## Settled runtime contracts

- One bot session owns one TCP connection. `--clients N` starts several concurrent sessions only against loopback hosts; same-IP remote fan-out is rejected by NewtonWars. A manager run records one SQLite capture per map (revised 2026-11-27, P19): the first session records shared world events once and rolls the capture over at each map boundary it detects, and each session tags its own identity/energy events and outbound commands with its bot name.
- The client uses the NewtonWars protocol version 8. Keep transport, typed protocol events, and bot policy in separate modules.
- SQLite recording defaults on and stores parsed semantic inbound events and outbound commands in sequence order per capture. A multi-client manager records shared world events once and tags bot-specific events and commands; it does not store raw TCP bytes. `--no-record` disables it; `--dummy` opts into the simple energy-gated firing policy.
- One capture is one map (P19; this replaced "one connection's complete replay log"). Captures of one invocation share `session.id` and number maps in `session.map_index`. A capture that starts at a boundary is self-contained: it opens with the known state as events (game mode, each bot's `own_id`, the new map's positions received up to the boundary) plus the latest energies in `initial_state` metadata. `map.duration_ms` exists only for a map observed from boundary to boundary (round timing is unavailable before the first full map; never guess it). A capture with fewer than `MIN_COMPLETED_PATHS` (3) completed paths is deleted when it closes. Older captures may hold several maps; replay tools keep splitting them at each `Planets` message, which is a no-op split for per-map captures. Oracle maps are used automatically when present for boundaries and scoring, never as fit input.
- Map boundaries and the end card are detected from the event stream alone (`src/map_change.rs`), since competitive servers send no `Planets`: an uninterrupted run of positions that moves every known player (>= 2), a lone player's reposition not explained by a shot ending at its old position, or a later `Planets`. One boundary signal drives the targeting `BotState` reset of every session and, on the first session, the live map reset and the capture rollover. Board mode (no shot of any player finishing for 1.5 s while at least 3 non-debris shots fly; shots still launch and energy still grows on the end card, so neither is evidence) pauses all commands except energy requests until a shot finishes or a new map starts. A shot's first recorded point is its launch position, so fit paths across player position changes together when the map is unchanged.
- The client rate limiter is per TCP connection: 16 outbound wire bytes per second with a 512-byte burst. Upstream refills one byte every three loop steps and exempts localhost, so its actual wall-clock rate depends on loop pace. Keep the client cap unless upstream source or limits change.
- NewtonWars only sends planet positions when launched with `sendplanets 1`.
- Targeting is opt-in and separate from transport. It prioritizes simulated hits; uncertainty probing is considered only without a predicted hit and above a threshold. The canonical connection feeds a background planet estimator (`src/estimator/`, v2: flat world by default; the fit compares the model field with the field implied by the observed paths (windowed, exact engine kernel, no dynamics simulated); the likelihood (P13, `noise.rs`) is the exact measurement floor (f32 rounding covariance plus interpolation variance) plus a model-error process for planets not found yet: per path and axis a Matern-3/2 process in arc length with sd `s * 100 / d` and length `l * d / 100`, `d = max(d_U, rho0)`, `d_U` the distance to the admissible region of unseen planet centres (10-unit raster over battlefield and margin: in the battlefield by 20, farther than `r + 20` from found planets and 20 from observed ticks) and `rho0 = sqrt(|U| / (pi N_u))` the typical distance to the nearest unseen planet (`N_u = max(24 - K, 0.5)`), so the background stands for the distant unseen planets and a near pass is left for a birth; whitened exactly by a Kalman filter with data-independent gains; `s` and `l` are a type-II MAP estimate (log-normal hyperprior around 0.07 and 600, `s <= 1`; the bound is binding while many planets are missing and measured better than a wider one) on the prequential residuals of the last 8 paths before the current one (each against the maintained search map just before that path's local refit, so within a batch of paths it includes the refits of the batch's earlier paths; rows within `r + 20` of a map planet are missing there), so a path is fitted under a background that has not seen it; a third scalar, the sd of a white excess noise on every row (log-normal prior around 1e-6, far below the f32 floor, so exact captures are unaffected), is estimated jointly with the other two on those series plus the current path's (only the white sd is kept; a decade scan first, because the likelihood is flat far below the floor), so white position noise is absorbed without a smooth planet signature being absorbed; the noise is computed from the maintained search map (never from the polished published map, so a polish cut by its wall ceiling cannot change later search) and frozen within each slice, local refit, polish and audit comparison, so every compared map sees the same noise (per-map noise with an unseen-count variance was tried and rejected: births were adopted for shrinking the noise); the fit's Levenberg-Marquardt solver (`lm.rs`, P12b) is a port of the `levenberg-marquardt` crate's Moré trust region on a QR reduced in parallel from row blocks of the Jacobian (never normal equations: E8 found different minima), the crate kept only as the test reference; K planets are searched on thinned rows and kept as one best-estimate map, no alternative modes; the evidence prior (odds 1/20 per planet) is heuristic, not calibrated (a Poisson(24) count prior was rejected: it makes data-free planets free); capped by `--planets N` when given, else `max_planets`). The search is resumable and incremental, replacing the greedy-birth search wholesale (2026-11-27, git history is the only fallback): each new path gets a local refit of the planets within 100 units of it (300 evaluations; rows thinned to at most 1000, 2 per 14-unit cell, strongest first) and the map is published at once; then up to `slices_per_path` (6) search slices of `slice_evaluations` (300) evaluations, each with a wall ceiling (`slice_ceiling`, 250 ms), run on the background estimator thread whenever no event is queued. A slice continues births (candidates from the unexplained windows, alone fits, joint partial refits, adoption on evidence, a death trial after each birth) whose state survives across slices and new paths; evaluation counts are the deterministic work limit (the same paths and settings give the same belief whatever the load while no slice ceiling cuts and no audit is adopted) and the wall ceilings plus `PartCeilings` are reported, never silent (`UpdateReport`). After the slices the published map gets a full-row refit under the same likelihood (600 evaluations, no guard), which also supplies the covariance (`not_computed` until then; still all-or-nothing). A background audit (8 paths, then every 16; half of the threads; never blocks publication) rebuilds the map from scratch (births on thinned rows at caps 500, 1000, 2000, then births and deaths on all rows, under the noise of the audit's start) and replaces the maintained map atomically only if its evidence on all rows, under the noise of the comparison's start, is higher. `Settings::audit_enabled` is off by default so replays are deterministic, and since P13 the live map leaves it off too (with the P13 likelihood it changed nothing on the dev worlds through 32 paths at 2.2 times the CPU). `SearchLimit` is `planet_cap`, `work_budget` (search work still pending) or `time_budget` (a slice hit its wall ceiling). Early updates (under 8 paths) have no special rule; with the P13 likelihood recall is higher than before at 8 and 60 paths but lower at 16-32 paths, while spurious planets are far fewer (known limitation). A planet is born only from trajectory evidence; surface contacts add a gated surface constraint but never create a planet, and contradicting contacts are reported as unmatched rather than overriding the fit. Target mode uses an empty map until the first fit, unless local oracle-map use is explicitly enabled. Map resets clear shot history, the pending search and the audit, and invalidate older fit results; fitting is cooperatively cancelled on reset and shutdown. Targeting continues using the latest published belief while fitting proceeds. Live observations and fits remain sequential; candidate refits within a slice run in parallel. The uncertainty score is a cheap marginal-variance exposure proxy, not posterior information gain; all targeting sessions share its map.
- Targeting simulates against the physical planet map plus a residual correction (P17, 2026-11-27, `src/estimator/residual.rs`; the older residual field and field-only source hypothesis removed 2026-11-26 stay gone): the posterior mean of the P13 model-error process along each observed path against the published map (exact Kalman filter and RTS smoother of the `noise.rs` state-space model; rows within `r + 20` of a map planet unobserved, as in the scale estimate), spread on a 15-unit raster as the nearest observed cell's local average times the Matern-3/2 correlation of the distance at the process length (median of `l * max(d_U, rho0) / 100` over the rows; the off-path spread is a heuristic, not a 2D posterior), zero within one cell of every planet disk. It is built with every published belief from that belief's map (a birth explains part of the residual, so a correction never outlives its map); gated without any compute when the largest process sd `s * 100 / max(rho0, 20)` is below `GATE_ACCELERATION` (2e-4, about one unit of drift over 100 ticks), and not applied when its largest value is below that; the reason is recorded (`residual_correction_unavailable_reason`), never a silent zero. The belief records the model scalars (`residual_model`), so a recorded decision rebuilds the same correction from its map and the capture's paths (`estimator::residual_correction`). The fit never sees it and it never creates a planet. Physical covariance remains explicitly unavailable where not identified.
- Planet count (P18): `--planets N` (`planets = N`, `EINSTEINBOT_PLANETS`) is a known total and is used as fixed, not as a prior centre: `N - K` unseen planets for the model-error cutoff `rho0` and cap `N`. Without it the unseen count is the mean excess over `K` of a broad prior on the total (discrete Gaussian, centre 24, sd 4, 1..64; `noise::unseen`; this is not the evidence prior over K), and the cap stays `DEFAULT_MAX_PLANETS`. Never hardcode 24 elsewhere. `ResidualModel::total_planets` records the count a correction was built with.
- Stopping (P18): the first Ctrl+C, or a session whose server closes or drops the connection, stops the sessions, prints the in-memory per-map statistics of the last three map epochs (P19 boundaries) at once (`game_stats::immediate_report`), lets each of those maps' estimators settle for up to 1 s (`LiveMap::settle`, newest first; the live map keeps the two previous epochs' estimators for this) and prints each settled map as it arrives (`settled_report`, truth-scored when `Planets` disclosed the map), then exits. A second Ctrl+C prints the in-memory part if it is not out yet and exits at once. Statistics go to stderr; truth only scores, never feeds the estimator.
- The live publication path does no per-path re-simulation: `model_position_rmse` is not computed live (always `None`; offline tools use `estimator::position_rmse`). The observed ticks are stamped incrementally (`noise::TickMask`), the model-error estimate memoizes each series' likelihood per model, and the residual correction smooths paths in parallel; all exact.
- Targeting tracks per-map spatial coverage from completed trajectories. The coverage grid is a diversity heuristic; predicted hits retain priority, probes are discounted by novelty, and approach penalties are bounded. A possible planet contact alone must not veto or penalize a shot; simulation still accounts for planets in the current map. Missing covariance must remain explicitly unavailable, never presented as certainty.
- Do not penalize shots merely for being close in launch parameters to a previous shot: small adjustments can improve aim. Use actual observed trajectories and outcomes when refining a shot; keep predicted-hit priority and do not treat a possible planet impact as a categorical veto.
- Local manager variants use the same targeting policy with coarse angle steps of 8, 10, and 12 degrees and one-degree refinement of promising candidates; keep policy differences explicit and small until capture comparisons justify distinct roles. Search respects available energy and the server velocity limit. Predicted hits are ranked by flight time to impact (shorter first), then predicted impact offset, then lower energy. Without a predicted hit or an information shot, the bot waits until it has `APPROACH_MIN_ENERGY` (15) before firing an approach shot. A decision waits for the map at most 500 ms, then uses the latest published belief (P15, 2026-11-27). Player collision predictions use latest known positions and physics substeps. Captures record per-decision state and build revision in metadata.

## Verification

- The Cargo `dev` profile uses `opt-level = 1` for Einsteinbot and `opt-level = 2` for dependencies; debug information and incremental compilation retain their defaults. Use the normal dev profile for local runs and scenario tools, `cargo check` for quick compile feedback, and `cargo test` for behavior checks. Use release builds only for optimized runtime and performance comparisons.
- Run `cargo fmt --check` and `cargo test` for Rust changes.
- Use the normal dev profile for `cargo run` commands unless measuring optimized performance; use `--release` for those comparisons.
- Live client checks may use an already-running local NewtonWars listener on port 3490. Do not start a second server if one is already running.

## Map inspector

- Prefer visual representations (layers, glyphs, timeline strips, bars) over additional tables, text or numbers; add text only where a visual cannot carry the information (user policy, 2026-11-27).
